### Locked Decisions

- **D-01:** Solo **4 límites** distinguen los planes; todo lo demás es igual en todos:

  | Límite | Gratis | Pro | Clínica |
  |---|---|---|---|
  | Pacientes (mascotas) | 50 | ilimitados | ilimitados |
  | Veterinarios activos | 1 | 1 | 2 / 3 / 5 según tramo (guardado en el plan) |
  | Logo de la clínica en carné/PDF/página | no (solo nombre) | sí | sí |
  | Protocolos propios (crear/editar en Más > Protocolos, "Guardar en mi catálogo") | no (estándar) | sí | sí |

- **D-02:** **Nunca se limita**: carné, link público, PDF del carné, compartir por WhatsApp, alertas de vacunas (una a una), registrar dosis, agenda, historia clínica y su PDF, leer/exportar datos, autoría.
- **D-03:** Al llegar a 50 en Gratis **solo se bloquea crear pacientes (mascotas) nuevos**, incluido el alta combinada cliente+mascota y "agregar mascota". Clientes sin mascota, ver, atender, vacunar, agendar y compartir siguen igual.
- **D-04:** "Paciente" = **todas las mascotas registradas** en la clínica (conteo simple; borrar mascotas libera cupo).
- **D-05:** El pie **"Hecho con VetApp"** se mantiene en **todos** los planes (confirma Fase 5 D-19).

Los links ya compartidos **siguen funcionando** (solo pierden el logo). Protocolos propios ya creados siguen usándose para el cálculo de próximas dosis; en Gratis no se pueden crear ni editar nuevos.
- **D-07:** El plan lo cambia **el dueño del producto** con una **función de soporte** `asignar_plan(clinica_id, plan, tramo/miembros_max, pagado_hasta, fundador)` ejecutable **solo por service_role** (vía SQL Editor o el conector de Supabase con autorización). Ningún usuario de la app puede cambiar su propio plan (privilegios por columna / RLS / RPC definer, patrón 4.1). Sin panel ni códigos de activación.

## Summary

La fase se resuelve casi entera con **un delta SQL idempotente al final de `schema.sql`** y una feature Flutter pequeña (`lib/features/plan/`). El hallazgo central es que el enforcement más barato y robusto no es reescribir RPCs ni policies existentes, sino **triggers `BEFORE` con códigos SQLSTATE propios** (`LP001..LP004`): `mascotas_insert` ya permite al veterinario insertar directamente (no solo vía RPC), `registrar_dosis`/`guardar_protocolo` son `security definer` (bypassan RLS) y un trigger los cubre a todos sin copiar 100+ líneas de cada función. Las únicas funciones que sí hay que redefinir son `generar_invitacion_clinica`, `consumir_invitacion`, `carne_publico` y `carne_de_mascota`.

El plan vigente se calcula en **una sola función interna `_plan_efectivo(p_clinica, p_hoy)`** (mismo patrón que `_carne_filas(..., p_hoy)`), con fechas como `date` en hora de Bogotá (`_hoy_bogota()` ya existe) para que el smoke test sea determinista. Toma el candidato de mayor jerarquía entre: Beta, plan pagado (con `pagado_hasta`), prueba Clínica, prueba Pro y Gratis, cada uno con su gracia. "Colegas en solo lectura" se expresa con `puede_escribir()` (los primeros `miembros_max` miembros activos ordenados por admin primero y antigüedad pueden escribir; el resto, no) más un trigger guard por tabla de escritura; un trigger da un error determinista y mapeable, mientras que una policy restrictiva haría que UPDATE/DELETE fallen en silencio con 0 filas.

Riesgos reales: (1) Google Play — el botón de WhatsApp es una decisión ya tomada (D-14) pero la interpretación del revisor no está verificada; mitigar con copy neutro y un define vacío que oculta el botón. (2) El smoke test existente (193 checks, bloques P y Q) crea clínicas nuevas, que ahora nacen en prueba Pro de 1 vet; los tests de 4.1 que unen colegas pasan solo si la prueba Clínica se abre al generar el primer código y trae cupo ≥ 4 (se recomienda 5). (3) La aplicación en vivo exige autorización del usuario y que él pegue el smoke test (el clasificador bloqueó el envío por MCP en 4.1).

**Primary recommendation:** Un solo bloque `-- ===== Fase 5.1 =====` al final de `schema.sql` con: tabla `clinica_planes` (sin escritura para `authenticated`), `_plan_efectivo`, `mi_plan`, `puede_escribir`, 4 triggers de límite/guard (mascotas, logo, protocolos, solo-lectura), redefinición de las 4 funciones listadas y `asignar_plan` solo `service_role`; Dart consume únicamente `mi_plan()` y traduce `LP001..LP004` a una hoja explicativa.

### Pattern 1: Plan efectivo como función única (patrón `_carne_filas`)
**What:** `_plan_efectivo(p_clinica uuid, p_hoy date default _hoy_bogota())` devuelve una fila con plan, origen, estado, fechas y límites. Todo trigger/RPC/`mi_plan` la usa; Dart nunca recalcula fechas.
**When to use:** cualquier decisión "¿puede esta clínica X hoy?".
**Estado:** `sin_vencimiento` (Gratis/Beta sin fin) · `vigente` · `gracia`. El plan "Vencido" se muestra como Gratis con `ultimo_vencimiento` informativo.
**Example (boceto; el ejecutor debe completarlo y probarlo):**
```sql
-- Source: patrón _carne_filas (schema.sql líneas 2144+) + decisiones D-01..D-13
create or replace function public._plan_efectivo(p_clinica uuid, p_hoy date default public._hoy_bogota())
returns table (
  plan text, origen text, estado text, fundador boolean,
  vigente_hasta date, gracia_hasta date, dias_restantes int,
  miembros_max int, pacientes_max int, logo_permitido boolean, protocolos_propios_permitidos boolean
)
language sql stable security definer set search_path = public
as $$
  with p as (select * from public.clinica_planes where clinica_id = p_clinica),
  cand(rango, plan, origen, miembros_max, hasta, gracia) as (
    -- hasta NULL = sin fin. Beta dura mientras fundador o beta_hasta sea null/futura; sin gracia.
    select 3, 'beta', 'beta', 999, case when p.fundador then null else p.beta_hasta end, 0
      from p where p.plan = 'beta'
    union all  -- plan pagado: 15 días de gracia
    select case p.plan when 'clinica' then 2 else 1 end, p.plan, 'pagado',
           case p.plan when 'clinica' then p.miembros_max else 1 end, p.pagado_hasta, 15
      from p where p.plan in ('pro', 'clinica')
    union all  -- prueba Clínica: tramo de 5, 15 días de gracia
    select 2, 'clinica', 'prueba_clinica', 5, p.prueba_clinica_hasta, 15
      from p where p.prueba_clinica_hasta is not null
    union all  -- prueba Pro: sin gracia (D-10: al vencer → Gratis)
    select 1, 'pro', 'prueba_pro', 1, p.prueba_pro_hasta, 0
      from p where p.prueba_pro_hasta is not null
    union all  -- siempre hay un candidato (también si falta la fila)
    select 0, 'gratis', 'gratis', 1, null, 0
  ),
  elegido as (
    select c.* from cand c
    where c.hasta is null or p_hoy <= c.hasta + c.gracia
    order by c.rango desc, (c.hasta is null or p_hoy <= c.hasta) desc, c.hasta desc nulls first
    limit 1
  )
  select e.plan, e.origen,
         case when e.hasta is null then 'sin_vencimiento'
              when p_hoy <= e.hasta then 'vigente' else 'gracia' end,
         coalesce((select fundador from p), false),
         e.hasta, case when e.gracia > 0 and e.hasta is not null then e.hasta + e.gracia end,
         case when e.hasta is not null then (case when p_hoy <= e.hasta then e.hasta else e.hasta + e.gracia end) - p_hoy end,
         e.miembros_max,
         case when e.plan = 'gratis' then 50 end,
         e.plan <> 'gratis', e.plan <> 'gratis'
  from elegido e
$$;
```
Notas: usar `null` para "sin fin" (no `'infinity'::date`, evita depender de aritmética con infinito). Revocar a `public, anon, authenticated` (ver Pitfall 2).

### Pattern 2: `puede_escribir()` + trigger guard (solo lectura)
**What:** `puede_escribir()` es `true` si el llamador es veterinario activo y su posición en `row_number() over (order by (rol_clinica='admin') desc, created_at, id)` entre los activos de su clínica es ≤ `miembros_max` del plan efectivo. Un trigger `BEFORE INSERT OR UPDATE OR DELETE` genérico lo exige.
**Cuándo `auth.uid()` es null** (SQL Editor, service_role, Edge Function): el guard deja pasar.
**Tablas con guard (recomendado):** `clientes`, `mascotas`, `mascota_pesos`, `citas`, `cita_mascotas`, `consultas`, `dosis_aplicadas`; más las policies de storage `mascota_fotos_*` (`and public.puede_escribir()`).
**No** poner guard en `carne_enlaces` ni `vacuna_alertas` (D-02: compartir y alertas "nunca se limitan") — ver Open Question 3.
```sql
create or replace function public.guard_solo_lectura()
returns trigger language plpgsql security definer set search_path = public
as $$
begin
  if auth.uid() is not null and not public.puede_escribir() then
    raise exception 'Tu clínica está en modo de solo lectura. Pide al administrador que active un plan.'
      using errcode = 'LP004';
  end if;
  if tg_op = 'DELETE' then return old; end if;   -- ¡return new en DELETE cancela el borrado!
  return new;
end $$;
```

### Pattern 3: Límite de pacientes con advisory lock
```sql
create or replace function public.mascotas_validar_limite()
returns trigger language plpgsql security definer set search_path = public
as $$
declare v_max int; v_n int;
begin
  select pacientes_max into v_max from public._plan_efectivo(new.clinica_id);
  if v_max is null then return new; end if;                     -- Pro/Clínica/Beta: sin tope
  perform pg_advisory_xact_lock(hashtextextended('mascotas:' || new.clinica_id::text, 0));
  select count(*) into v_n from public.mascotas where clinica_id = new.clinica_id;
  if v_n >= v_max then
    raise exception 'Llegaste a los % pacientes del plan Gratis. Con Pro registras pacientes ilimitados.', v_max
      using errcode = 'LP001';
  end if;
  return new;
end $$;
```
El alta combinada (`registrar_cliente_con_mascota`) inserta cliente y luego mascota dentro de una sola función; si el trigger falla, **toda** la llamada hace rollback (no queda cliente huérfano). No hay que tocar las RPC.

### Pattern 4: Prueba Clínica atómica en `generar_invitacion_clinica`
Después del check de admin: `select ... from clinica_planes where clinica_id = v_clinica for update` (serializa), calcular plan efectivo y activos; si `activos >= miembros_max`: si el plan efectivo es `gratis`/`pro` y `not prueba_clinica_usada` → `update ... set prueba_clinica_hasta = _hoy_bogota() + 30, prueba_clinica_usada = true`; si no → `raise ... errcode 'LP002'`. Luego sigue el código existente tal cual. `consumir_invitacion` repite el chequeo de cupo (el plan puede vencer entre generar y usar) con el mismo `for update` sobre la fila del plan.

### Pattern 5: Logo oculto sin romper links
En `carne_publico` y `carne_de_mascota` reemplazar `'logo_path', cl.logo_path` por `'logo_path', case when (select logo_permitido from public._plan_efectivo(cl.id)) then cl.logo_path end`. La Edge Function `carne` ya firma solo si `logo_path` es un string válido y borra `logo_path`; con `null` devuelve `logo_url: null` y no cambia (no hay que redesplegarla). La página no se ve afectada: ya maneja "sin logo" (D-26). La pantalla de edición del admin (`supabase_clinica_repository`) sigue leyendo `clinicas.logo_path` crudo para mostrar el logo conservado con aviso "se mostrará al activar Pro".

### Anti-Patterns to Avoid
- **Reescribir `registrar_dosis`/`guardar_protocolo`/`actualizar_clinica` completas** solo para agregar un `if`: son largas y se redefinen al final del archivo; un trigger evita divergencias.
- **Calcular días restantes o vigencia en Dart con `DateTime.now()`**: el reloj del dispositivo puede estar mal o en otra zona; usar `dias_restantes`/`estado` del servidor.
- **Exponer `_plan_efectivo(uuid)` a `authenticated`**: permitiría consultar el plan de cualquier clínica por id (fuga entre tenants). Solo `mi_plan()` es público.
- **Banner de 80 % para miembros en solos**: con `miembros_max = 1`, 1/1 = 100 % siempre; sería ruido permanente. Aplicar 80 % solo a pacientes y avisar de cupo de miembros únicamente cuando `miembros_max ≥ 2` y está lleno.
- **Códigos SQLSTATE de clase 40** (`40001`...): PostgREST los reintenta como transitorios [CITED: supabase.com/docs/guides/troubleshooting/high-cpu-and-infinite-transaction-retries-when-using-custom-error-codes-in-rpc-functions-77326b]. `LP001..LP004` no lo son.

## Common Pitfalls

### Pitfall 1: Funciones nuevas quedan ejecutables por `authenticated`
**What goes wrong:** `revoke ... from public, anon` no quita el grant directo de `authenticated` que Supabase concede por defecto a funciones nuevas en `public`; `asignar_plan` quedaría llamable por cualquier usuario.
**Why it happens:** privilegios por defecto de Supabase (el propio schema documenta el hardening 0028/0029, líneas 1034-1041) [VERIFIED: codebase]; el patrón correcto ya existe en `carne_publico` (línea 3156: `revoke all ... from public, anon, authenticated; grant ... to service_role`).
**How to avoid:** para `asignar_plan`, `_plan_efectivo`, `consumir_invitacion` y funciones de trigger: `revoke all ... from public, anon, authenticated`; solo `asignar_plan` recibe `grant execute ... to service_role`. Smoke test: `has_function_privilege('authenticated', 'public.asignar_plan(...)', 'execute')` debe ser `false`.
**Warning signs:** advisor de seguridad lista `asignar_plan` como "executable by authenticated".

### Pitfall 2: Función de trigger invoker llama a una función revocada
**What goes wrong:** si `mascotas_validar_limite()` no es `security definer`, falla con `permission denied for function _plan_efectivo` cuando la ejecuta un usuario.
**How to avoid:** todas las funciones de trigger de esta fase son `security definer set search_path = public` (como `crear_perfil_nuevo_usuario`). `auth.uid()` sigue resolviendo al usuario real dentro del definer.

### Pitfall 3: `return new` en un trigger BEFORE DELETE
**What goes wrong:** en DELETE `new` es null → el borrado se cancela en silencio.
**How to avoid:** `if tg_op = 'DELETE' then return old; end if;` (ver Pattern 2) y un check del smoke test que borre una fila con guard permitido.

### Pitfall 4: Re-ejecutar `schema.sql` completo
**What goes wrong:** el archivo se re-ejecuta entero; los bloques viejos recrean `carne_publico`, `consumir_invitacion`, etc. y luego el bloque 5.1 al final debe volver a sobreescribirlas (gana la última). Si alguien edita la versión vieja "en su lugar" la divergencia es silenciosa.
**How to avoid:** poner las 4 redefiniciones **solo** en el bloque 5.1 con un comentario `-- redefinida en Fase 5.1` junto a la versión original (convención ya usada en 4.1 y 5, p. ej. línea 1115). Triggers: `drop trigger if exists ... ; create trigger ...`.

### Pitfall 5: Smoke test existente se rompe por el nuevo gating
**What goes wrong:** las clínicas del test nacen en prueba Pro de 1 veterinario. Los checks P (unir colegas) pasan solo porque `generar_invitacion_clinica` abre la prueba Clínica; con cupo menor que 4 (vet_a, a2, a3, a4) fallan. Los inserts directos a `clinica_invitaciones` (líneas 1520, 1536, 1585) no pasan por `generar_...` pero fallan antes por vencida/revocada/CLIENTE, así que no chocan con el cupo.
**How to avoid:** prueba Clínica = tramo de 5 [ASSUMED A3]; correr los 193 checks tras el delta *antes* de agregar el bloque R; ajustar cualquier check que asuma "sin límites". Para probar el tope de 50 hay que poner la clínica de prueba en Gratis con UPDATE como `postgres` y `generate_series`.

### Pitfall 6: Alta de un colega vía signup aborta con error opaco
**What goes wrong:** si `consumir_invitacion` lanza `LP002` desde `crear_perfil_nuevo_usuario`, Auth responde su 500 genérico (ya documentado como Pitfall 3 de 4.1).
**How to avoid:** chequear cupo también al **generar** el código (error claro al admin); en `unirse_a_clinica` (usuario ya autenticado) el mensaje sí llega. Aceptar la degradación en signup y documentarla.

### Pitfall 7: UPDATE/DELETE bloqueado por RLS no da error
**What goes wrong:** repositorios que hacen `.update(...).select().single()` reciben `PGRST116` (0 filas) y muestran "No encontramos la mascota".
**How to avoid:** por eso el guard es trigger (error `LP004`), no policy restrictiva; además el mapeo `LP004` debe estar en **todos** los repositorios de escritura (clientes, mascotas, citas, consultas, vacunación) vía el helper compartido, y la UI debe deshabilitar acciones con `puedeEscribirProvider`.

### Pitfall 8: Fechas
**What goes wrong:** `DateTime.parse('2026-10-31')` en Dart da medianoche local; `.toUtc()` puede mostrar el día anterior. Comparar contra `DateTime.now()` del dispositivo da días restantes distintos al servidor.
**How to avoid:** `pagado_hasta` es `date` **inclusivo** (último día pagado) en hora de Bogotá; el servidor devuelve `dias_restantes`; Dart solo formatea `dd/MM/yyyy` sin convertir zona. Documentar a quien use `asignar_plan`: "fecha = último día incluido".

### Pitfall 9: `now()` es constante dentro de la transacción del smoke test
**What goes wrong:** no se puede "esperar" a que venza un plan.
**How to avoid:** como `postgres`, `update clinica_planes set pagado_hasta = public._hoy_bogota() - 1` (gracia) y `- 16` (vencido + gracia agotada); o llamar `_plan_efectivo(clinica, p_hoy => fecha)`.

### Pitfall 10: Reducir `miembros_max` con `asignar_plan` deja colegas en solo lectura al instante
**What goes wrong:** la gracia solo existe por vencimiento; un downgrade manual por soporte tiene efecto inmediato.
**How to avoid:** `asignar_plan` devuelve jsonb con el plan efectivo resultante y emite `RAISE NOTICE` si `activos > miembros_max`.

### Pitfall 11: Marca y copy
**What goes wrong:** el mensaje prellenado de WhatsApp y las hojas dicen "VetApp"; el renombrado a Rondavet está detenido por compuertas.
**How to avoid:** constante única `kNombreApp` (o la existente si ya hay una) para el copy nuevo; no escribir el nombre en literales sueltos.

## Security Domain

### Applicable ASVS Categories

| ASVS Category | Applies | Standard Control |
|---------------|---------|-----------------|
| V2 Authentication | no (sin cambios) | Supabase Auth existente |
| V3 Session Management | no | JWT de Supabase; el guard re-evalúa `activo` en cada consulta (patrón 4.1) |
| V4 Access Control | **sí** | Autorización en servidor: triggers + RPC definer; `clinica_planes` select-only por clínica; `asignar_plan` solo `service_role`; sin SELECT cross-tenant de planes (`_plan_efectivo` no expuesta) |
| V5 Input Validation | **sí** | Validación en `asignar_plan` (plan, tramo 2..50, fechas obligatorias en planes pagos); CHECK constraints en la tabla |
| V6 Cryptography | no | — |
| V13 API/Web Service | sí | `revoke ... from public, anon, authenticated` explícito; sonda anónima en `verify_live_schema.sh` |

### Known Threat Patterns for Supabase/PostgREST

| Pattern | STRIDE | Standard Mitigation |
|---------|--------|---------------------|
| Usuario edita su propio plan por PostgREST (`PATCH /clinica_planes`) | Tampering / Elevation | Sin policies de escritura + `revoke insert,update,delete,truncate ... from authenticated`; smoke test lo intenta y espera 0 filas/42501 |
| Llamar `asignar_plan` con JWT de usuario | Elevation | Sin EXECUTE para `authenticated`/`anon` + `if auth.uid() is not null then raise` |
| Consultar el plan de otra clínica con `_plan_efectivo(uuid)` | Information disclosure | Función interna revocada; `mi_plan()` usa `mi_clinica_id()` |
| INSERT directo en `mascotas` evitando la RPC para pasar los 50 | Tampering | Trigger `BEFORE INSERT` (no depende de la RPC); advisory lock contra carreras |
| Colega en solo lectura escribe vía RPC `security definer` | Elevation | Trigger guard dispara también bajo owner (a diferencia de RLS) |
| Subir logo directo al bucket en Gratis (consumo de almacenamiento) | Tampering | Agregar `logo_permitido` a policies `clinica_logos_insert/update` además del trigger de `clinicas`; UI hace pre-chequeo |
| Enumeración de planes/clínicas | Information disclosure | Tabla filtrada por `mi_clinica_id()`; sin RPC pública |
| Reintento infinito por SQLSTATE transitorio | Denial of service | No usar clase 40 |
