# Phase 2 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

---

## Scope

**Design tokens are LOCKED from Phase 1** (`.planning/phases/01-fundaci-n/01-UI-SPEC.md`, approved). This phase does **not** redefine colors, typography, or spacing — it applies the existing tokens to new screens and defines two new reusable visual patterns (filter/selector chips, pet photo avatar) that Phase 1 didn't need.

**In scope (screens):**
- `ClientesListScreen` (`/clientes`) — replaces `_ComingSoonScreen`. Search + list of cliente cards.
- `ClienteDetailScreen` (`/clientes/:id`) — view/edit cliente, mascotas list (CLI-04), "Vincular cuenta" action (CLI-05).
- `NuevoClienteMascotaScreen` (`/clientes/nuevo`) — combined cliente+mascota create flow (D-02), the primary path.
- `MascotaFormScreen` reused standalone (D-03: existing cliente + new pet, reached from `ClienteDetailScreen`).
- `PacientesListScreen` (`/pacientes`) — replaces `_ComingSoonScreen`. Search + especie filter chips + list of mascota cards.
- `MascotaDetailScreen` (`/pacientes/:id`) — ficha (foto, datos, peso history), edit action.
- **Vincular cuenta** dialog/bottom-sheet — shown from `ClienteDetailScreen`, displays the generated 6-digit code (CLI-05). No dedicated route.

**Out of scope (belongs to later phases):**
- Historia clínica timeline/consulta screens (Phase 3).
- The CLIENTE-side "reclamar código" screen and "Mis mascotas" (DIR-06, Phase 9).
- Agenda, vacunación, inventario, facturación, dashboard metrics (Phases 4–8).
- Dark-mode re-verification (still provisional/derived per Phase 1's note — not re-touched this phase).

## Typography

Reused verbatim from Phase 1 — same 4 roles, same 2 weights (400, 600). No new sizes/weights introduced.

| Role | Size | Weight | Line Height |
|------|------|--------|-------------|
| Body | 16px | 400 (Figtree) | 1.5 |
| Label | 14px | 600 (Figtree) | 1.5 |
| Heading | 20px | 400 (Caprasimo) | 1.2 |
| Display | 28px | 400 (Caprasimo) | 1.2 |

**Usage mapping for this phase's screens:**
- Display (28px Caprasimo): not used this phase (reserved for brand moments like Login — none exist here).
- Heading (20px Caprasimo): `AppTopBar` screen titles ("Clientes", "Pacientes", "Nuevo cliente"), section titles inside the combined create flow ("Datos del dueño", "Datos de la mascota"), the mascota/cliente name at the top of each detail screen (e.g. "Rocky", "Rita Gómez").
- Body (16px Figtree/400): card row text (nombre, teléfono, raza, edad), form field values, weight-history entries, "Vincular cuenta" dialog body text.
- Label (14px Figtree/600): `AppTextField` labels ("Nombre *", "Teléfono *", "Especie *"), filter chip labels ("Todos", "Perros", "Gatos", "Otros"), button labels ("Guardar", "Nueva mascota", "Tomar foto"), the 6-digit code itself in the vinculación dialog (rendered large — see Copywriting Contract).

**Focal point per screen:**
- `ClienteDetailScreen` / `MascotaDetailScreen`: the subject's name (Heading, Caprasimo) directly under the top bar is the primary visual anchor — everything else (fields, mascotas list, weight history) is secondary to it.
- `NuevoClienteMascotaScreen`: no single focal point by design — D-02 requires the flow to read as one continuous sequence, so both section headings ("Datos del dueño" / "Datos de la mascota") carry equal visual weight; the single "Guardar" button at the bottom is the only accent-colored element competing for attention.
- Vinculación dialog: the 6-digit code is the focal point — rendered larger than standard Label size is ever used elsewhere (see Copywriting Contract for the exact treatment).

## New Component Patterns (introduced this phase)

Phase 1 shipped no chip or photo-picker widget. Both are needed now and must be built as reusable `core/widgets/**` components (not one-off screen code) so later phases (Agenda's day filter, Inventario's stock-level filter) can reuse them without redefining the visual language.

### `AppFilterChip`
- **Visual:** rounded-pill outline (`border` color, `surface` fill) when inactive; solid `primary` fill with `onPrimary` (white) text when active — matches `DESIGN-REFERENCE.md`'s "chips de filtro" pattern ("outline redondeado, estado activo con fondo sólido").
- **Radius:** full pill (`AppSpacing.radiusLg` or greater — same rounding family as `AppCard`/`AppStatusChip`).
- **Label:** Label role (14px/600 Figtree).
- **Touch target:** minimum 44px height including padding.
- **Two uses this phase, same widget:**
  1. Especie selector in the create/edit mascota form — single-select, one of "Perro" / "Gato" / "Otro" (D-04: this is how the required `especie` field is captured, not a text input — faster than typing per the zero-friction principle).
  2. Species filter row on `PacientesListScreen` — single-select, one of "Todos" / "Perros" / "Gatos" / "Otros" (per `DESIGN-REFERENCE.md`'s existing mockup pattern), filters the visible list client-side against the already-fetched/searched result set (does not trigger a new debounced query — filtering is instant, no network round-trip).

### `AppPhotoPicker`
- **Visual:** a circular avatar (96px on `MascotaDetailScreen`, 56px on list cards) showing the pet's photo via `CachedNetworkImage` (with `cacheKey` = the stable `foto_path`, per 02-RESEARCH.md Pitfall 1 — **non-negotiable**, verify at implementation time that `cacheKey` is passed) once a photo exists; when no photo exists, shows a neutral placeholder (paw-print icon per the brand mark, on `surfaceMuted` background — never a broken-image icon or empty gray box).
- **Camera-first tap (D-05):** tapping the avatar (or its overlay camera badge, `primary`-colored, positioned bottom-right of the circle) opens the device camera **directly** — no intermediate action-sheet/menu. A separate, visually secondary text button below or beside the avatar, "Elegir de galería", offers the gallery as the explicit alternate path. This is the concrete implementation of D-05: one tap → camera, zero menus.
- **States:** default (no photo, placeholder), uploading (avatar dims + centered small spinner, no layout shift), populated (photo + camera badge still visible to signal "tap to change"), error (photo failed to load — falls back to placeholder, does not show a broken-image icon; a failed *upload* surfaces the Error Copy below via a snackbar, not inline on the avatar).

## Screen-by-Screen Interaction Contract

### `ClientesListScreen`
- Top: `AppTextField`-style search input (no visible label per search-field convention — placeholder "Buscar por nombre o teléfono"), **no search button, no Enter requirement** — every keystroke feeds the 350ms-debounced `search()` (D-06, per 02-RESEARCH.md Pattern 2). Results re-render in place as they arrive.
- Below: list of `AppCard` rows, one per cliente — nombre (Body, 600 not used; use Label weight via bold Body per existing `AppCard` text convention), teléfono (Body, `textSecondary`), and mascota count badge ("2 mascotas" / "Sin mascotas", `textMuted`).
- Floating primary action: "Nuevo cliente" → `NuevoClienteMascotaScreen`. Accent-colored, per the "one CTA per screen" rule.
- Tapping a row → `ClienteDetailScreen`.

### `ClienteDetailScreen`
- Heading: cliente's `nombre` (Heading role).
- Editable fields rendered as `AppTextField`s pre-filled with current values; an explicit "Editar" action (or inline always-editable fields, planner's implementation choice) — either way, changes save via "Guardar cambios" (accent CTA), not auto-save-on-blur, so the vet has a clear confirmation moment.
- "Mascotas" section (CLI-04): list of `AppCard` mini-rows (mascota nombre + especie icon), each tappable → `MascotaDetailScreen`. Below the list: "Nueva mascota" button (`AppButtonVariant.outline`, not the screen's primary accent slot — the screen's one accent CTA is reserved for "Guardar cambios") → opens `MascotaFormScreen` standalone, pre-filled with this `clienteId` (D-03).
- "Vincular cuenta" row (CLI-05): a labeled action ("Vincular cuenta" with a link/QR icon), tapping it opens the vinculación dialog (see below). If the cliente already has an unexpired code, the dialog reopens showing the same code + remaining time instead of generating a new one; if expired or none exists, it generates on open.

### Vinculación dialog (bottom sheet)
- Triggered from `ClienteDetailScreen`, not a route.
- Content: short explanatory line ("Comparte este código con {nombre} para que vincule sus mascotas desde su cuenta"), the 6-digit code rendered large and monospaced-feeling (Heading-sized treatment even though it's not a heading — visually the focal point of the sheet), expiry note ("Válido por 24 horas"), and a "Copiar código" action (`AppButtonVariant.outline`).
- No "share via WhatsApp" deep-link this phase (that pattern is reserved for AGND-05 in Phase 4) — copy-to-clipboard is the only share mechanism, consistent with D-07's scope note that this phase only builds the vet-side generate/display half.
- Dismissing the sheet does not invalidate the code (it remains claimable until `codigo_expira_en`).

### `NuevoClienteMascotaScreen` (combined create, D-02)
- **Single `SingleChildScrollView`, no `PageView`/stepper, no "Siguiente" button between sections** — this is the literal implementation of D-02's "flujo combinado y continuo."
- Section 1 ("Datos del dueño"): `AppTextField` "Nombre *", `AppTextField` "Teléfono *" (`keyboardType: phone`). No other cliente fields shown here — email/dirección/notas are edit-later fields per D-04, not part of the zero-friction create path.
- Section 2 ("Datos de la mascota"): `AppTextField` "Nombre *", `AppFilterChip` especie selector "Perro / Gato / Otro *", `AppPhotoPicker` (camera-first per D-05).
- **Optional fields are collapsed by default** (D-04): a single "Agregar más detalles" expandable disclosure (chevron icon, `textMuted` label, no accent color — it's a secondary affordance) reveals raza, fecha de nacimiento, and peso inline when tapped. Collapsed state is the default render — the zero-friction minimum path (nombre + especie) must be reachable and submittable without ever touching this disclosure.
- Bottom: single "Guardar cliente y mascota" primary button, disabled (not hidden) until the four required fields (cliente nombre, cliente teléfono, mascota nombre, especie) are filled — disabled state uses reduced opacity, not a color change, per the "accent never on disabled" rule above.
- On submit: calls the `registrar_cliente_con_mascota` RPC (atomic, per 02-RESEARCH.md Pattern 4) — the UI shows a single loading state on the button (`AppButton.isLoading`), not a multi-step progress indicator, reinforcing the "one gesture" feel D-01 asks for.

### `MascotaFormScreen` (standalone, D-03 path)
- Identical Section-2 fields from the combined flow (same `AppFilterChip`, same `AppPhotoPicker`, same collapsed-details disclosure) rendered alone, no Section 1 — reached from `ClienteDetailScreen`'s "Nueva mascota" button with `clienteId` already known and never re-asked.
- Also reused, pre-filled, for **editing** an existing mascota from `MascotaDetailScreen`'s edit action — same fields, submit label changes to "Guardar cambios" instead of "Nueva mascota".

### `PacientesListScreen`
- Same search-as-you-type pattern as `ClientesListScreen` (350ms debounce, no submit action), placeholder "Buscar por nombre, dueño o especie".
- Below search: `AppFilterChip` row ("Todos" / "Perros" / "Gatos" / "Otros") — filters the current result set client-side, does not re-query.
- List: `AppCard` rows with the 56px `AppPhotoPicker` thumbnail (read-only here, tapping the row — not the thumbnail — navigates), nombre (Heading-weight emphasis via bold Body, not literal Heading role — list density matters more than display typography here), raza + edad on a secondary line (`textSecondary`), dueño nombre on a tertiary line (`textMuted`).
- Primary action: none floating on this screen — pet creation always flows through a cliente (D-02/D-03), so there is no "Nuevo paciente" button divorced from an owner. This is intentional, not an oversight: it enforces that every mascota has a known dueño from the moment of creation.

### `MascotaDetailScreen`
- Heading: mascota's `nombre`.
- `AppPhotoPicker` at 96px, camera-first tap to replace photo.
- Ficha fields (especie, raza, fecha de nacimiento → edad calculada, dueño — tap dueño name to jump to `ClienteDetailScreen`) rendered read-only with an "Editar" action → `MascotaFormScreen` pre-filled.
- "Historial de peso" section (PAT-05): reverse-chronological list of `peso_kg` + `registrado_en` (formatted `dd/MM/yyyy` per `intl`), each entry a plain row (not a card — lighter visual weight than the mascotas-list cards, since this is a sub-section, not the screen's primary content), newest first. A "Registrar peso" text action (not accent-colored primary — this screen's one accent CTA is "Editar" if present, or none if the vet is just viewing) opens a minimal single-field entry (numeric peso input + implicit `now()` timestamp).
