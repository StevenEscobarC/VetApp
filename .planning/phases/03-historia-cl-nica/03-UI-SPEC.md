# Phase 3 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

---

## Scope

**Design tokens are LOCKED from Phase 1** (`.planning/phases/01-fundaci-n/01-UI-SPEC.md`, approved) and already applied app-wide by Phase 2. This phase does **not** redefine colors, typography, or spacing — it extends one existing screen and adds one new screen, reusing every token and shared widget already shipped.

**In scope:**
- **`MascotaDetailScreen` (`/pacientes/:id`, `/clientes/:id/mascotas/:mascotaId`) — extended, not replaced.** Adds a "Historia clínica" section (HIST-02 timeline) below the existing "Historial de peso" section, an "Exportar PDF" action in the top bar (HIST-03), and demotes the existing "Editar" button so "Nueva consulta" can hold the screen's one accent CTA slot (see Screen-by-Screen Contract — this is a required change to already-shipped Phase 2 UI, not a new decision Phase 2 got to make).
- **`ConsultaFormScreen` (new, `/pacientes/:id/consultas/nueva`, `/clientes/:id/mascotas/:mascotaId/consultas/nueva`)** — "Nueva consulta" create form (HIST-01), reusing the exact collapsed-optional-details interaction pattern `MascotaCamposSection` (Phase 2) already established, applied to consulta fields instead of pet fields.
- **PDF export flow (HIST-03/D-04/D-05)** — triggered from the ficha's top bar, no dedicated screen; native OS share sheet only.

**Out of scope (explicitly excluded this phase, not deferred to "later" — do not build any UI for these):**
- "Grabar nota de voz" — the approved mockup's screen 4 literally shows this button next to "Nueva consulta," but it maps to DIFF-03 (v2 diferenciador). **Do not render it at all** — not even disabled/no-op. A disabled button implies "coming soon," which is not true; omitting it entirely keeps the screen honest about what this phase actually does (zero-friction principle: no UI for features that don't exist).
- Editing or deleting a saved consulta (HIST-04) — no edit icon, no swipe-to-delete, no context menu on any timeline entry, ever.
- Linking a correction to the consulta it corrects (D-01) — no "corrige a…" field or picker anywhere.
- Any "próxima cita" scheduling UI (deferred to Phase 4) or attachment/photo UI on a consulta (deferred, `adjuntoUrls` not built).
- A PDF preview screen or in-app PDF viewer — the flow is generate → hand bytes to `Printing.sharePdf` → native share sheet. No intermediate preview screen.
- Dark-mode re-verification (still provisional/derived per Phase 1's note — not re-touched this phase).

## Typography

Reused verbatim from Phase 1 — same 4 roles, same 2 weights (400, 600). No new sizes/weights introduced.

| Role | Size | Weight | Line Height |
|------|------|--------|-------------|
| Body | 16px | 400 (Figtree) | 1.5 |
| Label | 14px | 600 (Figtree) | 1.5 |
| Heading | 20px | 400 (Caprasimo) | 1.2 |
| Display | 28px | 400 (Caprasimo) | 1.2 |

**Usage mapping for this phase's screens:**
- Heading (20px Caprasimo): `AppTopBar` titles ("Paciente", "Nueva consulta"), the "Historia clínica" section title on the ficha (same `titleMedium`/Caprasimo treatment `_HistorialPeso`'s "Historial de peso" heading already uses — match it exactly, do not introduce a different heading style for the new section).
- Body (16px Figtree/400): consulta diagnóstico summary line (collapsed timeline card), all expanded detail text (anamnesis, tratamiento, evolución, vital-sign values), all `AppTextField` values in the form.
- Label (14px Figtree/600): timeline card date (`formatearFecha`, same `bodyMedium`/`textSecondary` treatment `_HistorialPeso` already uses for its date column — reuse, don't invent a new date style), form field labels ("Diagnóstico *", "Tratamiento *", "Anamnesis", "Peso (kg)", etc.), vital-sign field labels inside the expanded card ("Temperatura", "Frecuencia cardíaca", etc.), "Agregar más detalles" disclosure label.

**Focal point:**
- `MascotaDetailScreen` (unchanged from Phase 2): the mascota's `nombre` (Heading, Caprasimo) directly below the photo is the primary visual anchor. The new "Historia clínica" section is a secondary section, visually equal in weight to "Historial de peso" — neither competes with the name for focal attention.
- `ConsultaFormScreen`: no single focal point by design, matching `NuevoClienteMascotaScreen`'s precedent — "Diagnóstico \*" and "Tratamiento \*" (the two required fields) carry equal, elevated visual weight versus the collapsed optional section; the single "Guardar consulta" button at the bottom is the only accent-colored element.

## Color

60/30/10 split, reused verbatim from Phase 1 (already wired in `app_colors.dart`):

| Role | Value | Usage this phase |
|------|-------|-------|
| Dominant (60%) | `#F5EAD8` (`background`) | Screen background on `MascotaDetailScreen` (unchanged) and `ConsultaFormScreen` |
| Secondary (30%) | `#EEE7DB` (`surface`) + `#DCD3C4` (`border`) | Timeline entry `AppCard` backgrounds, `AppTextField` fills (`#EBDDC5` `surfaceMuted`) in the consulta form |
| Accent (10%) | `#C67139` (`primary`) | Reserved for, and **only** for: the "Nueva consulta" primary button (the screen's one accent CTA — see the "Editar" demotion below), the "Guardar consulta" primary button on `ConsultaFormScreen`, the focus/ring state on the currently-edited form field, the active bottom-nav icon+label (existing, unchanged) |
| Destructive | `#DC2626` | Not used this phase — HIST-04 is enforced structurally (no update/delete exists anywhere in the UI, per Scope), so there is no delete confirmation surface that would need this color |

**Required change to already-shipped Phase 2 UI — "Editar" loses the accent slot:** `MascotaDetailScreen`'s existing "Editar" button (`AppButton`, currently default/`primary` variant) must change to `AppButtonVariant.outline`. The approved mockup explicitly calls "Nueva consulta" the ficha's *primary* button, and the "one accent CTA per screen" rule (locked since Phase 1, reused in Phase 2) means only one button on this now-busier screen can hold it. "Nueva consulta" is this phase's core value-add action (HIST-01) and wins the slot; "Editar" (an occasional, non-clinical action) is demoted — the same reasoning Phase 2 already used to demote `ClienteDetailScreen`'s "Nueva mascota" to outline when "Guardar cambios" needed the slot. "Registrar peso" stays a text action, unchanged, per Phase 2's own precedent.

Accent is never applied to: timeline card backgrounds, body/detail text inside an expanded card, the "Exportar PDF" top-bar icon (icon buttons in the app bar use the default/foreground icon color, not accent — matching how no top-bar action anywhere in Phases 1–2 uses accent color either), or more than one primary CTA per screen.

## New Component Patterns (introduced this phase)

### Consulta timeline entry (no new shared widget — feature-local pattern)

**What it replaces:** nothing existing — this is Phase 3's first timeline-of-structured-records UI (Phase 2's "Historial de peso" is a flat list of single numbers, not applicable as a direct template beyond ordering/date-formatting conventions).

- **Visual:** `AppCard`, one per consulta, stacked with `AppSpacing.sm` gaps (not a `Divider`-separated flat list like weight history — these entries carry enough content to warrant card boundaries).
- **Collapsed state (default):** a single row — `formatearFecha(consulta.fecha)` on the left (Label role, `textSecondary`, same treatment as the weight-history date column), the diagnóstico text on the next line below (Body, single line, `TextOverflow.ellipsis` if it doesn't fit), and an expand chevron (`Icons.expand_more`, `textMuted`) aligned to the trailing edge of the date row.
- **Expanded state (tap anywhere on the card to toggle — local `bool` per card, no navigation, no new screen):** chevron flips to `Icons.expand_less`; below the diagnóstico line, render in this fixed order, each as a Label heading + Body value pair:
  1. **Anamnesis** — value text, or `Sin registrar` (`textMuted`) if `null`.
  2. **Examen físico** — only rendered as a sub-block if `!examenFisico.estaVacio`; each present vital sign as its own `Label: value` line (e.g. "Peso: 4.2 kg", "Temperatura: 38.5 °C", "Frecuencia cardíaca: 90 lpm", "Frecuencia respiratoria: 24 rpm", "Mucosas: rosadas"). If `examenFisico.estaVacio` is `true`, render one line: "Examen físico: Sin registrar" instead of five empty rows — never show five "Sin registrar" lines for a skipped exam, one line covers it.
  3. **Diagnóstico** — repeated here in full (the collapsed summary may have been truncated) — always present, never "Sin registrar" (HIST-01/D-03 requires it).
  4. **Tratamiento** — always present, never "Sin registrar".
  5. **Evolución** — value text, or `Sin registrar` if `null`.
- **Ordering:** newest first, defensive client-side sort by `fecha` descending — same non-negotiable pattern `_HistorialPeso` already applies ("nunca confía ciegamente en el orden que entrega la fuente de datos").
- **No icon/action for edit or delete** on any card, ever — this is the visual enforcement of HIST-04, matching the weight-history precedent exactly.
- **"Sin registrar" convention:** identical wording and `textMuted` styling already used elsewhere on the ficha (raza, fecha de nacimiento) — do not invent a different empty-value phrase for consulta fields.

### `ConsultaFormScreen` — reuses `MascotaCamposSection`'s disclosure pattern, not a new widget

**What:** The exact interaction shape of `MascotaCamposSection` (Phase 2) — required fields always visible at the top, optional fields collapsed behind a single "Agregar más detalles" disclosure — applied to consulta fields. This is a feature-local screen (`lib/features/clinical_history/presentation/screens/consulta_form_screen.dart`), not a shared `core/widgets` component, since no other feature needs "diagnóstico/tratamiento required, exam vitals optional."

- **Always visible, at the top of the form (D-03 required fields):**
  - `AppTextField` "Diagnóstico *" — multiline (`maxLines: null` or a small fixed multiline height, matching how a clinical free-text field should read, not a single-line input).
  - `AppTextField` "Tratamiento *" — multiline, same treatment.
- **Collapsed by default, behind "Agregar más detalles" (identical chevron + `textMuted` label treatment to `MascotaCamposSection`):**
  - `AppTextField` "Anamnesis" — multiline.
  - A "Examen físico" sub-heading (Label role) followed by: `AppTextField` "Peso (kg)" (numeric, decimal keyboard — same `parsearPeso`-style validation as `_RegistrarPesoSheet`, reused, not reinvented), "Temperatura (°C)" (numeric, decimal), "Frecuencia cardíaca (lpm)" (numeric, integer), "Frecuencia respiratoria (rpm)" (numeric, integer), "Mucosas" (free text, single line).
  - `AppTextField` "Evolución" — multiline.
- **Primary button "Guardar consulta"** (accent, per Color contract above) at the bottom — **disabled (not hidden), reduced opacity, until Diagnóstico and Tratamiento are both non-empty** — identical enabling rule and visual treatment to `NuevoClienteMascotaScreen`'s "Guardar cliente y mascota" button (D-03 zero-friction: anamnesis/examen físico/evolución never gate submission, matching the confirmed decision).
- **Loading state:** `AppButton.isLoading` on submit — one spinner on the button, no separate multi-step progress indicator, matching the established "one gesture" feel.
- **On success:** pop back to `MascotaDetailScreen` (no intermediate confirmation screen), show a snackbar "Consulta guardada", and the caller must invalidate `consultasProvider(mascotaId)` **and** — only if a `pesoKg` was entered — `pesosProvider(mascotaId)` (D-02/Pitfall 3: the weight history section must reflect the new weight without the vet needing to separately open "Registrar peso").
- **No "cancelar" confirmation dialog** on back navigation — this is a create-only form with no destructive discard risk beyond standard unsaved-input loss, consistent with every other create form in this app (none of them confirm-on-back either).

### "Exportar PDF" action (top bar, no new screen)

- **Placement:** `AppTopBar`'s `actions` list on `MascotaDetailScreen`, icon-only (`Icons.picture_as_pdf_outlined`), default/foreground icon color (not accent — see Color contract).
- **Accessibility:** `Tooltip`/`Semantics(label: "Exportar historia clínica a PDF")` — it is icon-only, same accessibility discipline `AppPhotoPicker`'s camera badge already established in Phase 2.
- **Loading state:** while `HistoriaClinicaPdfService.generar()` runs (font fetch + document assembly), replace the icon with a small `CircularProgressIndicator` sized to fit the app-bar action slot (matching the existing `AppButton.isLoading` spinner-swap pattern, applied to an icon button instead) and disable re-tap — never show a second, competing full-screen loading overlay.
- **On success:** call `Printing.sharePdf(bytes:, filename:)` directly — no in-app preview, no confirmation dialog (D-05: this is exactly like sharing any file from the OS, no extra app-level ceremony).
- **On failure:** snackbar, see Copywriting Contract.
- **Disabled state:** if the mascota has zero consultas, the action is still tappable (D-04 exports "the whole history," which can legitimately be empty) — do not disable it; `HistoriaClinicaPdfService.generar()` must handle an empty list gracefully (a PDF with just the header and no entries), not error out. This avoids adding a special-case empty-state branch to the top-bar action.

## Screen-by-Screen Interaction Contract

### `MascotaDetailScreen` (extended)

Section order, top to bottom (locked — matches the approved mockup's own screen-4 ordering: datos básicos → peso → timeline → primary consulta action):
1. Photo avatar, nombre (Heading) — unchanged from Phase 2.
2. "Editar" button — **now `AppButtonVariant.outline`** (demoted, see Color contract).
3. Ficha fields (especie, raza, fecha de nacimiento, dueño) — unchanged.
4. "Historial de peso" section — unchanged from Phase 2 (including its own "Registrar peso" text action).
5. **"Historia clínica" section (new):** heading ("Historia clínica", same `titleMedium` treatment as "Historial de peso"), the timeline (consulta cards, newest first, empty state if none), then the **"Nueva consulta" primary button** (`AppButtonVariant.primary`, icon `Icons.add`) directly below the timeline — this is the screen's one accent CTA.

`AppTopBar` gains the "Exportar PDF" icon action (title stays "Paciente", unchanged).

### `ConsultaFormScreen` (new)

- `AppTopBar(title: 'Nueva consulta')`, no actions.
- Body: single `SingleChildScrollView`, no stepper/`PageView` — same "one continuous flow" principle `NuevoClienteMascotaScreen` established for D-02, applied here for the analogous reason (zero-friction: a quick control visit should never feel like a multi-step wizard).
- Field layout and disclosure behavior: see "New Component Patterns" above.
- Reached only via the "Nueva consulta" button on `MascotaDetailScreen` — `mascotaId` is always known, never re-asked (same discipline as `MascotaFormScreen`'s D-03 path never re-asking `clienteId`).
